# Tunnel API: feasibility spike

**Status:** spike, 2026-11-12. Nothing here is production code. Spike tests live in
`viscorunner/src/test/java/com/viscosiety/viscorunner/spike/` and are off in the normal build
(see "Test pitfall" below). Run them with
`./mvnw test -pl viscorunner -Dtest='Tunnel*SpikeTest' -Dspike=true`.

Versions read: Tomcat 11.0.18 (test classpath; the image runs 11.0.14), Frank!Framework 10.3.0
(`frankframework-core-10.3.0-sources.jar`; `frankframework-security-10.3.0.jar` decompiled, no
sources jar), Spring Security 7.1.1 (decompiled).

The design under test: REST endpoints reachable only on an extra TLS connector (a "tunnel port"),
not on the public port 8080. Five parts: (1) a LifecycleListener adds the connector, (2) a Host
valve limits the tunnel port to `/runtime/api/**`, (3) a tunnel API servlet with its own login,
(4) a `TunnelApiListener` subclass hidden from the public `/api` by a filter, (5) a "public side
Off" setting.

## Summary

| Question | Verdict |
|---|---|
| Q1 TLS connector added at start | **Works.** Part (2) can be plain rewrite rules instead of a new valve. |
| Q2 Closing the public REST endpoints | **Works with a change.** `enabled=false` exists but kills every forward to `/api`; a SEALED authenticator closes direct calls and keeps forwards. |
| Q3 Filter order and lookup | **Works.** The filter runs after Spring Security, which does not leak existence (the 401 is path-independent). |

**Design-breaking finding (part 3):** a tunnel servlet that *forwards* to `/api/...` runs the
public `/api` security chain on the FORWARD dispatch. With the public side on the NONE
authenticator (ViscoForge's "Public" exposure) that chain only admits anonymous callers, so an
elevated forward is refused (the same 403 the platform's `call_api_endpoint` hit on 2026-10-23).
With `servlet.ApiListenerServlet.enabled=false` there is no `/api` servlet to forward to. So the
forward design only works for some public-side settings. **Recommended instead:** make the tunnel
servlet a subclass of `ApiListenerServlet` mapped at `/tunnel-api/*` that dispatches itself (no
forward). See Q2 and "Alternative for part 3".

## Q1: TLS connector added at start

**Verdict: works.**

Evidence: `TunnelConnectorSpikeTest` (6 tests, real embedded Tomcat, the image's own
`rewrite.config` with tunnel rules in front). The spike listener is
`TunnelConnectorSpikeListener`.

- The listener is a `LifecycleListener` on the **Server** and acts on `Lifecycle.BEFORE_INIT_EVENT`
  (`before_init`). It calls `server.findServices()[0].addConnector(connector)`. The Service then
  initialises the connector (binds the port) and starts it with the others. Adding later works too
  (`StandardService.addConnector` starts a connector added to a running service), but before_init
  keeps a bind failure inside the normal startup.
- Connector: `new Connector("org.apache.coyote.http11.Http11NioProtocol")`, `setPort`,
  `setScheme("https")`, `setSecure(true)`, `setProperty("SSLEnabled", "true")`, one
  `SSLHostConfig` with one `SSLHostConfigCertificate`, `connector.addSslHostConfig(host)`.
- **PKCS12 file:** `certificateKeystoreFile`, `certificateKeystorePassword`,
  `certificateKeystoreType=PKCS12`. Test `theListenerAddedATlsConnectorThatServesTheSameWebApplication`:
  HTTPS on the tunnel port reaches the same `/runtime` context (keystore generated by `keytool`
  in the test, SAN localhost).
- **PEM pair also works** (proven, not only read): `certificateFile` + `certificateKeyFile`
  (unencrypted PKCS#8 here; `certificateKeyPassword` for an encrypted key; `certificateChainFile`
  for intermediates). Test `aPemCertificateAndKeyPairWorkAsWell`. As server.xml attributes on
  `<Certificate>` the names are the same.
- **Which connector:** `request.getLocalPort()` returns the tunnel connector's port, and in a valve
  `org.apache.catalina.connector.Request#getConnector()` returns the very Connector object the
  listener added (asserted by identity). `request.isSecure()` is true there. Both are reliable:
  they come from the socket, not from a header. (`getServerPort()` comes from the Host header and
  must NOT be used.)
- **Absent setting:** `withoutTheSettingNoTunnelConnectorIsAddedAndNothingListens`: one connector,
  and a connect to the port is refused.
- **Part (2) needs no new valve.** Tomcat's `RewriteValve` variable `%{SERVER_PORT}` is
  `request.getLocalPort()` (read in `ResolverImpl.resolve`, decompiled). So the image's
  `rewrite.config` can carry the tunnel rules, placed BEFORE the old-path rules:

  ```
  RewriteCond %{SERVER_PORT} !^8080$
  RewriteRule ^/(runtime|viscolink)/api(/.*)?$ /runtime/tunnel-api$2 [L]
  RewriteCond %{SERVER_PORT} !^8080$
  RewriteRule ^/.*$ /tunnel-not-found [L]
  RewriteCond %{SERVER_PORT} ^8080$
  RewriteRule ^/(runtime|viscolink)/tunnel-api(/.*)?$ /tunnel-not-found [L]
  ```

  Tests: on the tunnel port `/runtime/api/x` and `/viscolink/api/x` (even GET + text/html, the
  old-path redirect case) reach the tunnel servlet; `/runtime/iaf/gui/`, `/runtime/tunnel-api/x`,
  `/console/`, `/` answer 404; on the public port `/runtime/api/x` is unchanged, the old-path
  redirect still works and `/runtime/tunnel-api/x` answers 404. The rules key on "not 8080", so
  they need no list of tunnel ports. (In the image `/tunnel-not-found` falls into the ROOT
  webapp, which should answer its own 404; not tested with ROOT.)

Pitfalls found:

- A rule with the bare pattern `^` did not match in Tomcat 11.0.18 (observed, cause not
  investigated); `^/.*$` does.
- A host-level RewriteValve that rewrites in place re-runs the whole Engine pipeline with the new
  URI (`RewriteValve.invoke`, decompiled: `connector.getService().getContainer().getPipeline().getFirst().invoke(...)`;
  a ThreadLocal stops the valve rewriting twice). Any other Host valve before it sees each request
  twice, once with the old URI. Another reason to do the routing in the rewrite rules.
- Embedded test only: `Tomcat.getConnector()` creates the default connector lazily and returns the
  service's FIRST connector, so call it before `start()` or it returns the tunnel connector.
- The 8080 public port is assumed fixed (the image, the probes and the gateway sidecar use it).
- Not checked: keystore rotation without restart (`Connector.reloadSslHostConfigs()` exists);
  client certificates (`SSLHostConfig.certificateVerification`).

**Test pitfall (affects the existing build):** Tomcat's `ConfigFileLoader.setSource` keeps only the
FIRST source set in a JVM (decompiled: `if (source == null) source = ...`), and `RewriteValve`
reads `rewrite.config` through it. So only the first embedded Tomcat in a surefire fork reads its
own rewrite rules. `RuntimeSessionCookieScopeTest` failed (404 instead of 302/200) whenever a spike
Tomcat started before it. The spike tests therefore set the rules with
`RewriteValve.setConfiguration(String)` and are off unless `-Dspike=true`. A real test added next
to `RuntimeSessionCookieScopeTest` should do the same, and that test itself should too.

## Q2: Closing the public REST endpoints ("Off")

**Verdict: works with a change.** Read in code; nothing run against a real Frank!Framework.

What exists (read):

- `servlet.ApiListenerServlet.enabled=false` exists. `ServletConfiguration.loadProperties` reads
  `servlet.<name>.enabled`; `ServletManager.register` then returns before
  `servletContext.addServlet` ("skip instantiating servlet ... not enabled"). Nothing is mapped to
  `/api/*`: a caller gets Tomcat's 404 (the default servlet; inferred, not run). **But an internal
  `RequestDispatcher.forward` to `/api/...` also lands on the default servlet: 404.** It also breaks
  the platform's own `AgentApiServlet` (`/api-service/api/*` forwards to `/api`), i.e. the
  assistant's `call_api_endpoint`. And `ApiListener.buildPhysicalDestinationName` and
  `OpenApiGenerator` read the `ApiListenerServlet` config/urlMapping (cosmetic: the `/api` prefix
  disappears from the console's listing).
- `AuthenticationType.SEALED` (`SealedAuthenticator`): HTTP Basic against an EMPTY user store with
  its own entry point that answers `sendError(401, "Access Denied, configure an authenticator to
  enable web access.")`. A direct call always gets 401. It must be declared as a named
  authenticator (only CONTAINER and NONE exist by default, `ServletManager.afterPropertiesSet`):

  ```
  application.security.http.authenticators=<existing list>,closed
  application.security.http.authenticators.closed.type=SEALED
  servlet.ApiListenerServlet.authenticator=closed
  servlet.ApiListenerServlet.securityRoles=<any non-empty list>
  ```

  **`securityRoles` must not be empty.** `ApiListenerServlet` declares no access-granting roles
  (`AbstractHttpServlet.getAccessGrantingRoles` = null), and
  `AbstractServletAuthenticator.addEndpoints` registers a servlet without roles as a PUBLIC
  endpoint (`permitAll`) whatever the authenticator. SEALED without roles = open.
- A forward through a SEALED chain: the chain's authorization is `authenticated()` (the default
  `getAuthorizationManager`). An elevated `PreAuthenticatedAuthenticationToken` put in the holder
  and in the request-attribute repository slot (what `AgentApiServlet` does) should pass. Inferred
  from `AgentApiServlet`'s live behaviour on OAuth2/YML chains; not run on SEALED.
- What the caller sees: SEALED -> 401 with a body naming "configure an authenticator" (reveals the
  setting, not the endpoints); `enabled=false` -> 404.
- NONE (`NoOpAuthenticator`) authorizes with `AuthenticatedAuthorizationManager.anonymous()`: only
  anonymous callers pass. This is why a forward with an elevated context is refused when the
  public side is "Public".

Recommendation: with the forward design, "Off" = SEALED + roles. With the alternative for part 3
(below) the tunnel path does not depend on `/api` at all, so "Off" can be `enabled=false` as long
as the platform gateway (`AgentApiServlet`) is changed the same way, or SEALED + roles to keep
the gateway as is.

### Alternative for part 3 (recommended)

`ApiListenerServlet.service` takes `request.getPathInfo()` as the URI and calls
`ApiServiceDispatcher.getInstance()` (a JVM singleton) directly. A subclass
`TunnelApiServlet extends ApiListenerServlet`, annotated `@IbisInitializer` in an
`org.frankframework.*` package (the component scan in `SpringEnvironmentContext.xml` only looks
there, which is why `AgentApiServlet` lives in `org.frankframework.visco.security`), overriding
`getName()` = `tunnelApi` and `getUrlMapping()` = `/tunnel-api/*`, gets its own
`servlet.tunnelApi.*` settings and its own Spring Security chain, and serves the same listeners
without any forward. Then: no `/api` chain runs for tunnel calls, the public authenticator does not
matter, per-listener AUTHROLE checks use the tunnel login, and `enabled=false` on the public side
is harmless to the tunnel. Points to handle: its `destroy()` clears the shared dispatcher (only at
shutdown; override to be safe); the servlet must itself refuse calls whose arrival port is 8080
(defence beside the rewrite rule); `servlet.tunnelApi.securityRoles` must be non-empty for Basic,
else the endpoint is public (same rule as above). Not run.

## Q3: Filter order and the listener lookup

**Verdict: works.** Ordering backed by `TunnelFilterOrderSpikeTest` (plain Tomcat stand-ins);
Frank!Framework/Spring wiring read in code.

- How filters get registered today: Spring Security's `springSecurityFilterChain` by
  `SecurityFilterChainConfigurer` (`@Order(HIGHEST_PRECEDENCE)`, extends
  `AbstractSecurityWebApplicationInitializer`): programmatic, `isMatchAfter=false`, `/*`, dispatcher
  types REQUEST, ERROR, ASYNC, FORWARD, INCLUDE. ViscoLink's own filters are added
  programmatically from Spring beans in `springConsoleSecurity.xml`
  (`ConsoleSecurityRegistrar.registerToolSecurity`: `servletContext.addFilter("consoleToolSecurity", ...)`,
  `isMatchAfter=false`, `/*`); `web.xml` declares only `consoleManifestCredentials`. There is no
  own `ServletContainerInitializer`. `AgentApiServlet` is an `@IbisInitializer` servlet registered
  by `ServletRegisteringPostProcessor` -> `ServletManager.register`.
- Order (test `aLaterProgrammaticFilterRunsAfterTheEarlierOneAndBeforeDeclaredFilters`):
  programmatic `isMatchAfter=false` filters run in registration order, before declared ones. A
  filter added from a Spring bean (as `ConsoleSecurityRegistrar` does) is registered after
  `springSecurityFilterChain`, so it runs AFTER Spring Security. Running before it would need a
  `WebApplicationInitializer` ordered before HIGHEST_PRECEDENCE (not possible) or a Tomcat-level
  valve.
- That order does not leak existence: the `/api` chain matches by the servlet's URL pattern
  (`URLRequestMatcher` over `/api/*`), not per listener. An unauthenticated public caller gets the
  same 401 for a tunnel-only endpoint, a public one and a nonexistent one. An authenticated (or, on
  NONE, anonymous) caller then gets the filter's 404, the same status `ApiListenerServlet` sets
  for an unknown URI (`response.setStatus(404)`, empty body). The filter must also answer 404
  (not 405) when the matched pattern belongs to a tunnel listener with another method.
- Lookup form: use exactly what `ApiListenerServlet.service` uses: method =
  `EnumUtils.parse(ApiListener.HttpMethod.class, request.getMethod())`, uri =
  `request.getPathInfo()` with one trailing `/` removed, leading `/` kept, relative to `/api`
  (in a filter mapped to `/api/*`, `getPathInfo()` is the target servlet's path info). Then
  `ApiServiceDispatcher.getInstance().findConfigForRequest(method, uri)` and
  `config.getApiListener(method)` (both public). Check `instanceof TunnelApiListener` over all of
  `config.getMethods()`, not only the requested method.
- Forward interplay (test `aRequestOnlyGuardDoesNotRunOnTheTunnelServletsForwardButSecurityDoes`):
  a filter mapped for REQUEST only does not run on the tunnel servlet's FORWARD; the security
  filter (all dispatcher types) does run again on the forward. That second fact is the cause of
  the design-breaking finding above.
- Registration in a Spring bean must survive a configuration reload: `ConsoleSecurityRegistrar`
  checks `getFilterRegistration(name)` first because `addFilter` throws once the context is up.

## Other things that make the design harder

- **`TunnelApiListener` registers fine** (`ApiListener.start` calls
  `ApiServiceDispatcher.registerServiceClient(this)`; nothing keys on the class). But tunnel and
  public listeners share ONE pattern table: the same uriPattern + method on both sides throws
  "has already registered" at start.
- **OpenAPI leaks tunnel endpoints:** `/api/openapi.json` (`generateOpenApiSpec` ->
  `OpenApiGenerator`) walks every registered pattern, so it lists tunnel listeners on the public
  side, with `/api` server URLs (`servlet.ApiListenerServlet.urlMapping`). The filter must also
  cover `openapi.json` (and the deprecated `<pattern>/openapi.json`), or the generator needs a
  filtered dispatcher view.
- The console's Web services page (`management/bus/endpoints/WebServices`) lists all ApiListeners
  too (inside the console only; probably fine).
- Unverified: using a subclass via `className` on `<ApiListener>` in a configuration (Frank!Doc /
  XSD validation of the class name).
- The old-path RewriteValve does not interfere when the tunnel rules come first (tested).
